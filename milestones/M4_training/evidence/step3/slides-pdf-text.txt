MODEL INPUTS AND OUTPUTS



No tensors: the model reads messages and writes text or tool calls

 Item               Format                                                       Size                 One turn, step by step
                                                                                                      1. Caller text is added to the conversation.
 System prompt      Role, working rules, current time, all 10 S-rules with IDs   ~1,100 tokens
                                                                                                      2. The harness checks whether it confirms the
                                                                                                      agent’s last question (a clear “yes” after a
 Tool schemas       JSON Schema for 9 tools; CRM fields use picklists            ~1,100 tokens        question).
                                                                                                      3. The LLM replies with text or tool calls.
 Retrieved facts    {results: [{id: "F2", text: …}]}, top 3                      34–116 tokens each
                                                                                                      4. Each tool call passes the validation layer, which
                                                                                                      runs it or refuses it with an error code.
 Conversation       Caller / agent turns + tool calls + JSON results             ≤ 12 caller turns
                                                                                                      5. Results go back to the LLM; up to 8 rounds per
                                                                                                      turn.
 Agent output       Text, or tool calls {name, arguments}; temperature 0         ≤ 800 tokens


 Measured           Average input per agent call in the M3 run                   ~2,170 tokens        The LLM can never create the confirmation itself.

THE TWO DESIGNS WE COMPARE



Same tools, same model, different structure

   BASELINE · B0                                                                        TREATMENT · M1

   Single agent · built in M3                                                           Multi-agent · built in M4
   • One LLM holds the whole conversation                                               • Conversation agent talks to the caller
   • Calls all 9 tools directly                                                         • Knowledge agent: grounded answers with fact IDs
   • Fewer hops: lower latency and cost                                                 • Qualification agent: missing fields
   • This is the baseline that ran the 10 tasks                                         • CRM / handoff planner: structured tool plans




Both designs share the tools, validation layer, LLM, simulator and evaluator, so any difference in results comes from the structure alone (decision rule O11).

WHY THIS ARCHITECTURE



Each choice is tied to our data, risks and budget

 Decision               Our choice                    Alternative                 Why ours here


 Business knowledge     Retrieval + rules in prompt   Fine-tune an LLM            ~15 rows per business: far too little to fine-tune; facts change


 Retrieval              BM25, 1 row per chunk         Embeddings + vector DB      5 short facts: BM25 finds the right one, free and deterministic


 CRM writes             Validation layer in code      LLM writes directly         Blocks wrong-record and unconfirmed writes (O2, O3)


 Outbound calls         Deterministic gate            LLM decides                 Consent rules need 0 violations (O7); code is auditable


 Order                  Text first, then voice        Voice from day one          Separates reasoning errors from speech errors; cheaper


 Voice stack            Cascaded STT → LLM → TTS      Speech-to-speech model      Keeps a transcript for tools, audit and scoring


 Evaluation             CRM end state + judge         Judge only; tool sequence   End state is objective; many correct tool orders exist

HOW WE EVALUATE



No training loss: we score behaviour and the final CRM

   reward = CUSTOM_DB × COMMUNICATE × PROJECT_SAFETY
   A task passes only if all three hold. Adapted from τ-bench: success is judged by the final database state, not by matching an exact tool sequence.




   CUSTOM_DB                                                    COMMUNICATE                                                  PROJECT_SAFETY

   CRM end state                                                Required information                                         Prohibited actions
   Code compares the whole final CRM with                       LLM judge checks each item the caller had                    LLM judge checks forbidden promises and
   the gold state. Objective. (O2)                              to be told. (O1, O4)                                         false “saved” claims; code logs blocked
                                                                                                                             writes. (O3, O5)




Why no loss: models are pretrained and used through prompts, retrieval and tools; ~15 facts and 40 tasks per business are far too few to fine-tune. In M4, “training” =
prompt, retrieval and model experiments on development tasks.
