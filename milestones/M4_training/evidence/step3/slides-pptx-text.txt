=== ppt/notesSlides/notesSlide4.xml ===
SRIJAN (~1.5 min): This is the full data flow. A caller speaks; in voice mode LiveKit carries the audio, Silero detects when they stop talking and Deepgram turns it into text. In M3 these grey boxes are replaced by a simulated caller that types. The text reaches the agent, the navy box, which is a pretrained LLM with nine tools. Before the call, preprocessing splits the knowledge file into one chunk per row: business rules go straight into the system prompt, and the factual rows go into a BM25 search index the agent queries. Every tool call goes down through the orange validation layer, which checks that the caller is verified and has just confirmed, before anything touches the CRM. The CRM is reset from the seed for every task. On the left, follow-up events go through the outbound gate, which is plain code, not an LLM. Orange means the safety decisions are never made by the model.

=== ppt/notesSlides/notesSlide5.xml ===
SRIJAN (~1 min): Here is each component with what it takes in and what it gives out. Only three parts use a pretrained model: the agent, the simulated caller and the judge. Everything that can change data or place a call is ordinary code: the tools, the validation layer, the CRM and the outbound gate. One component's output is the next one's input: the caller's text goes to the agent, the agent's tool calls go to the validation layer, its results go back to the agent, and at the end the evaluator compares the final CRM and the transcript with the answer key.

The multi-agent version, with a conversation agent and three specialists, is the M4 work. === ppt/notesSlides/notesSlide8.xml ===
SRIJAN (~1.5 min): Each choice comes from our situation, not from a general claim that it performs well. We have about fifteen facts per business, which is far too little to fine-tune, so the agent retrieves facts and always has the rules in its prompt. With only five short facts, BM25 keyword search finds the right one, costs nothing and gives the same answer every time. Writes and outbound calls are where real harm happens, so code decides them, not the model. We start in text so that speech errors don't hide reasoning errors. And we score by the final CRM state, because there are many correct orders of tool calls. Limitations are on slide 17.

=== ppt/notesSlides/notesSlide10.xml ===
SARWAR (~1.5 min): Our inputs are text, so instead of resizing or normalising we do six steps. We load and check the files. We split the knowledge file so each row becomes one chunk, keeping its ID and source, because splitting a rule in the middle could separate it from its exception. Rules go into the prompt so they always apply; facts go into the search index. Each task is split into four views, so the agent never sees the caller's goal or the answer key, and the code raises an error if it ever would. The CRM is reset per task, and only development tasks can be selected. Below is a real before-and-after sample. === ppt/notesSlides/notesSlide12.xml ===
OMKAR (~1.5 min): We do not train weights, so there is no training loss; the slide says why. Instead each task gets a reward that is the product of three checks, following tau-bench. First, code compares the entire final CRM with the gold state, which is objective. Second, an LLM judge checks that the agent told the caller everything required. Third, the judge checks that the agent did nothing prohibited and never claimed success without a successful tool result. If the judge cannot run, those two are reported as not judged, never as a pass. Each metric maps to an M1 objective.

=== ppt/notesSlides/notesSlide13.xml ===

Then the real LLM run: 5 of 10 tasks passed every check, the CRM was right in 7, and safety held in all 10. These are pipeline checks on ten tasks, not a performance estimate.

=== ppt/slides/slide12.xml ===
HOW WE EVALUATE
No training loss: we score behaviour and the final CRM
Presenter: Omkar Shankar Pawar
12 / 20
reward = CUSTOM_DB × COMMUNICATE × PROJECT_SAFETY
A task passes only if all three hold. Adapted from τ-bench: success is judged by the final database state, not by matching an exact tool sequence.
CUSTOM_DB
CRM end state
Code compares the whole final CRM with the gold state. Objective. (O2)
COMMUNICATE
Required information
LLM judge checks each item the caller had to be told. (O1, O4)
PROJECT_SAFETY
Prohibited actions
LLM judge checks forbidden promises and false “saved” claims; code logs blocked writes. (O3, O5)
Why no loss: models are pretrained and used through prompts, retrieval and tools; ~15 facts and 40 tasks per business are far too few to fine-tune. In M4, “training” = prompt, retrieval and model experiments on development tasks.
